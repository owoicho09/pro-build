# 1. PRODUCT VISION

We are building an AI-powered software-building platform for nontechnical users.

Think about the experience created by products such as v0 and Lovable, but our product extends beyond initial generation.

The platform should allow a person with little or no technical knowledge to:

1. Describe a software idea naturally.
2. Upload supporting files, images, screenshots, documents, logos, assets, etc.
3. Have the system understand what they are trying to build.
4. Reason about the product before coding when the request requires it.
5. Build the actual application.
6. Show the application in a live preview.
7. Allow the user to continue modifying the same application through natural-language requests.
8. Handle uploaded assets intelligently during later changes.
9. Identify external integrations/credentials that the application requires without stopping the rest of the build.
10. Publish the completed application.
11. Host/manage the production application.
12. Connect or eventually purchase/manage domains.
13. Allow the user to leave and return days or months later.
14. Continue developing the exact same project.
15. Publish new versions without unnecessarily disrupting the existing production version.

The relationship should feel like:

> Claude Code / v0 / Lovable for someone who does not know how to use a terminal, Git, deployment systems, environment files or DNS.

The user thinks about their **product**, not infrastructure.

The core lifecycle is:

IDEA
→ UNDERSTAND
→ PLAN WHEN NECESSARY
→ BUILD
→ VERIFY
→ PREVIEW
→ MODIFY
→ PUBLISH
→ DOMAIN
→ MANAGE
→ RETURN LATER
→ MODIFY AGAIN
→ REPUBLISH

A project is not a disposable generation.

It is a persistent software product.

# 2. IMPORTANT PRODUCT PRINCIPLE

We are NOT building a coding engine from scratch if v0 Platform API already provides the capability.

The initial builder engine should use the current v0 Platform API wherever appropriate.

v0 should potentially handle things such as:

* application generation
* project/chat continuity
* generated files
* code context
* file/image attachments
* live previews
* continued modifications
* error repair capabilities
* Vercel project/deployment integration

Do not recreate these systems unnecessarily.

However, do not tightly couple the entire business domain to v0.

Create a sensible builder/provider abstraction so that another engine could theoretically be introduced later without rewriting the entire SaaS.

For example, conceptually there may be a BuilderEngine/service boundary capable of operations such as:

* create project/build session
* send build/change request
* provide attachments/context
* retrieve project/build state
* retrieve preview
* continue an existing project
* retrieve generated artifacts/files where supported
* publish/deploy where supported

These are conceptual responsibilities, NOT mandatory method names.

Use the actual current v0 API/SDK rather than inventing endpoints based on this prompt.

V1 should use v0.

Future possibilities might include Claude Code, Codex, Vercel Sandbox or another builder.

Do NOT implement those alternative engines now.

# 6. PLANNING EXPERIENCE

Do not force every user through a long questionnaire.

The system should distinguish between requests that are sufficiently clear and requests where important product decisions are missing.

Example:

> Build a professional portfolio website for a wedding photographer. Here is her logo and photos.

This probably requires little planning.

But:

> Build an Uber-like logistics marketplace.

requires significantly more reasoning.

The planning experience should infer obvious requirements and only ask questions whose answers materially affect the product.

The user should never feel like they are filling out a 40-question software requirements form.

Where appropriate, produce a concise build understanding such as:

WHAT WE'RE BUILDING

USERS

CORE FEATURES

IMPORTANT WORKFLOWS

INTEGRATIONS

IMPORTANT ASSUMPTIONS

Then allow the build to proceed.

Planning must help the user.

It must not become friction.

WORKING/PREVIEW VERSION

VERIFY

USER APPROVES/PUBLISHES

# FINAL PRINCIPLE

Do not optimize for generating the most code.

Optimize for creating the smallest coherent architecture that delivers the complete experience.

We are building:

**a persistent AI software-building, deployment and management platform for nontechnical users.**

v0 is initially the underlying builder.

Vercel is initially the deployment/hosting/domain infrastructure.

Our product is the intelligent layer that makes the entire lifecycle understandable and manageable.

The experience should ultimately reduce software creation to:

**Describe → Build → Preview → Improve → Publish → Manage**

while preserving enough architecture, portability, security and persistence for the generated applications to be real software rather than disposable demos.

Begin with discovery and the ten checks.

Do not start implementation until those checks and the implementation plan are complete.
