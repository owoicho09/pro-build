We are now entering the PRODUCT UX REDESIGN + LAUNCH READINESS phase for proBuild.

IMPORTANT:
Do not begin by rewriting the application.
Do not throw away working architecture.
Do not replace working integrations simply because another implementation looks cleaner.
Do not treat this as a visual reskin.
Do not blindly add features from this specification.

The underlying product architecture has already been built and substantially live-tested against real Supabase, v0 Platform API, and Vercel resources.

Your first responsibility is to inspect the existing repository, database/schema, routes, components, BuilderEngine implementation, v0 integration, project persistence, build lifecycle, deployment implementation, attachments, secrets/integrations, credits, notifications, rate limiting, billing and domain work.

Understand what already exists before deciding what must change.

The purpose of this phase is to transform the existing technically-functional product into a polished, coherent AI software-building environment that feels native, persistent and trustworthy to nontechnical users.

The experience must NOT feel like a thin frontend sending API requests to v0.

==================================================
1. PRODUCT DEFINITION
==================================================

proBuild is a persistent AI software-building environment.

A user should be able to:

Describe what they want to build
→ create a persistent project
→ watch proBuild work
→ see a live preview
→ request changes conversationally
→ leave and return later
→ continue working on the same project
→ publish a chosen version
→ connect services/domains when necessary
→ maintain the project over time.

Users may also:

Browse templates
→ inspect an actual template preview
→ create their own project from that template
→ continue modifying it with AI.

The product should feel like:

"This is my project and proBuild is working on it with me."

NOT:

"I am submitting prompts to an API that generates websites."

Reference interaction philosophies include modern AI builders such as v0, Lovable and Bolt, while proBuild should deliberately reduce technical cognitive load for nontechnical users.

Do not clone any competitor visually.

A TEMPLATE is a reusable known project starting state.

11. USE TEMPLATE / CLONING
==================================================

"Use Template" should create a user-owned project from the known template starting state.

The resulting project must closely/exactly match the template preview because it originates from the same known source state.

Do not implement:

Template versioning should allow new projects to use the latest published template version while old projects retain their original state.

18. MESSAGE UX — CRITICAL
==================================================

The current experience reportedly feels like an API request:

- user sends message
- UI waits
- request feels detached
- refresh/reload may clear transient content
- conversation does not feel continuously present

Fix this fundamentally.

When the user sends a message:

1. render it immediately/optimistically
2. persist it immediately in proBuild's database
3. create/link the build asynchronously
4. keep it visible regardless of provider latency
5. update build state independently
6. preserve attachments
7. reconstruct everything correctly after refresh

The user should NEVER have to wait for v0 before seeing their own message.

Refresh must not erase sent messages.

Closing and reopening the project must reconstruct the conversation from persisted state.

The provider conversation is not the sole UI source of truth.

Possible mechanisms may include project/chat/source/Git repository based cloning, but DO NOT assume any API exists.

Inspect actual SDK types/current documentation available to the project.

If exact project-state cloning cannot safely be implemented with current v0 capabilities:

- do not fake it
- document the limitation
- propose the closest architecture that still guarantees template fidelity
- implement only after reasoning about the tradeoff

Template fidelity is more important than pretending a template system exists.
